# Roadmap: todolist-cli

## Overview

Build a zero-dependency CLI task manager in pure zsh, progressing from storage engine through CRUD operations, multi-list management, and culminating in the kanban visualization that is the project's core differentiator. Each phase delivers a working, testable capability that builds on the previous.

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions (marked with INSERTED)

Decimal phases appear between their surrounding integers in numeric order.

- [ ] **Phase 1: Project Scaffolding & CLI Dispatch** - Entry point, autoload structure, git-style subcommand routing
- [ ] **Phase 2: Storage Engine** - JXA-based JSON engine with atomic writes and directory structure
- [ ] **Phase 3: Core Task CRUD** - Create, edit, remove, and list tasks
- [ ] **Phase 4: Task Workflow** - Status transitions, completion, and priority assignment
- [ ] **Phase 5: Multi-List Management** - Multiple named lists with switching and defaults
- [ ] **Phase 6: Custom Statuses & Tags** - Per-list status definitions and task tagging with filters
- [ ] **Phase 7: Colored Output & List View** - ANSI color rendering for priorities and task display
- [ ] **Phase 8: Kanban View & Bulk Operations** - Inline kanban columns, responsive fallback, and bulk task ops

## Phase Details

### Phase 1: Project Scaffolding & CLI Dispatch
**Goal**: A working CLI entry point that dispatches subcommands and loads modules on demand
**Depends on**: Nothing (first phase)
**Requirements**: STOR-03
**Success Criteria** (what must be TRUE):
  1. User can run `todo` (or chosen command name) and see usage/help output
  2. User can run `todo <subcommand>` and it dispatches to the correct function
  3. Running the tool requires zero external dependencies -- pure zsh only
  4. Project follows zsh autoload/fpath pattern for modular function loading
**Plans:** 1 plan
Plans:
- [x] 01-01-PLAN.md -- Project structure, entry point, modules, and test suite

### Phase 2: Storage Engine
**Goal**: Reliable JSON data layer that all features depend on
**Depends on**: Phase 1
**Requirements**: STOR-01, STOR-02, STOR-04
**Success Criteria** (what must be TRUE):
  1. Data is stored in ~/.todolist/ with separate namespace directories per list
  2. JSON files can be read and written via osascript JXA without data corruption
  3. File writes use atomic write-to-temp + mv pattern (no partial writes on crash)
  4. Tasks have unique IDs generated by the storage layer
**Plans:** 1 plan
Plans:
- [x] 02-01-PLAN.md -- Storage engine module (_td_storage) with JXA JSON ops, atomic writes, and test suite

### Phase 3: Core Task CRUD
**Goal**: Users can create, view, edit, and delete tasks from the command line
**Depends on**: Phase 2
**Requirements**: TASK-01, TASK-02, TASK-03, TASK-04
**Success Criteria** (what must be TRUE):
  1. User can create a task with a title via `todo add "task title"`
  2. User can edit a task's title by referencing its ID
  3. User can remove a task permanently by ID
  4. User can list all tasks in the current list with readable formatted output
**Plans:** 2 plans
Plans:
- [x] 03-01-PLAN.md -- ID resolution helper, td-add, td-ls commands, integration tests
- [ ] 03-02-PLAN.md -- td-edit, td-rm commands, expanded tests, help text update

### Phase 4: Task Workflow
**Goal**: Users can move tasks through statuses and assign priorities
**Depends on**: Phase 3
**Requirements**: TASK-05, TASK-06, PRIO-01
**Success Criteria** (what must be TRUE):
  1. User can mark a task as completed (moves to final status)
  2. User can move a task to any status defined in the current list
  3. User can assign priority (alta/media/baixa) when creating or editing a task
**Plans**: TBD

### Phase 5: Multi-List Management
**Goal**: Users can organize work across multiple independent lists
**Depends on**: Phase 4
**Requirements**: LIST-01, LIST-02, LIST-03
**Success Criteria** (what must be TRUE):
  1. User can create a new named list via a single command
  2. User can switch active list with a single command
  3. When no list is specified, a default list is used automatically
  4. Each list stores its tasks independently (no cross-contamination)
**Plans**: TBD

### Phase 6: Custom Statuses & Tags
**Goal**: Users can define per-list workflows and categorize tasks with tags
**Depends on**: Phase 5
**Requirements**: LIST-04, TAG-01, TAG-02
**Success Criteria** (what must be TRUE):
  1. User can define custom statuses for each list (e.g., todo/doing/review/done)
  2. Custom statuses define the columns available for task movement
  3. User can add one or more free-form tags to any task
  4. User can filter displayed tasks by status and priority
**Plans**: TBD

### Phase 7: Colored Output & List View
**Goal**: Task display uses color coding for visual scanning
**Depends on**: Phase 6
**Requirements**: VIEW-01, PRIO-02
**Success Criteria** (what must be TRUE):
  1. Task listing uses ANSI escape codes for colored output
  2. High priority tasks display in red, medium in yellow, low in green
  3. Status and tags are visually distinguishable in the output
**Plans**: TBD

### Phase 8: Kanban View & Bulk Operations
**Goal**: Users see tasks in a visual kanban board and can operate on multiple tasks at once
**Depends on**: Phase 7
**Requirements**: VIEW-02, VIEW-03, TASK-07
**Success Criteria** (what must be TRUE):
  1. User can view tasks in kanban layout with columns rendered side-by-side per status
  2. Kanban columns auto-size based on terminal width
  3. When terminal is too narrow for side-by-side, view falls back to stacked list automatically
  4. User can perform bulk operations on multiple tasks at once (e.g., move, delete, tag)
**Plans**: TBD
